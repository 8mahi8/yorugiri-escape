# 夜霧の脱出 v0.5 — 4vs1再設計案（議論用・未承認）
更新: 2026-10-12 / Status: **DRAFT — 実装禁止（設計合意待ち）**

## 1. 方針
- 1人の操作キャラ + 味方サバイバーBOT3人 vs ハンターBOT1体。**オンライン対戦ではない**。
- 一番の快感は「仲間の行動がチャンスを作り、そのチャンスを使って目的を進める」こと。
- コア行動は **解読・チェイス・救助・潜伏/索敵**。特別な道具はこれを補助するに過ぎない。
- v0.4.1で起きた操作性の問題を繰り返さない。スマホ優先。ボタンを安易に増やさない。
- 第五人格の非対称協力構造をジャンルの参考にするが、キャラクター、演出、拘束装置、マップ、能力などはオリジナルにする。

## 2. 石投げについて — 暫定判断: コアから削除
### 必要性の検証
- **解決したい問題**: 潜伏した状態でハンターの注意をそらしたい。
- 1vs1では他の陽動者がいないので石の意義が大きかった。
- 4vs1では別の生存者がチェイスすること自体が自然な陽動。さらに味方救助・支援・解読という優先順位競合が生まれる。
- 石を全員に配ると、音を鳴らす→離れた場所を調査→解読、が単調な正解になりうる。
- タッチ操作の負担が重く、石を投げないと詰むバランスになるならルール側に欠陥がある。

**結論（仮）**: v0.5では石の標準装備/石補充を無効にし、UIボタンも消す。削除の可否はプレイテストで評価。
残すなら後の特定キャラの固有能力／使い切り陽動道具。A/B比較で、操作負担以上の戦略的選択肢を増やせる場合だけ復活。

## 3. 勝敗と試合の骨格
- 7つの修復対象のうち5つを起動。2か所の脱出ゲートを開き、マップ外へ出る。
- **3人以上脱出 = サバイバー勝利 / 2人 = 引き分け / 1人以下 = ハンター勝利**（仮）。
- プレイヤー本人が脱出失敗しても、仲間の行動を観戦し、チームの勝敗は最後まで確定させる。脱出した場合も同様。
- 初期ターゲット: 1試合約4〜7分。修復時間は4体の作業並列を考慮して後で計測・調整。
- 開幕から全員が修復するだけで自動勝利、またはハンターが全員の位置を知って即壊滅、どちらもNG。

## 4. 生存者の状態
- 健康 → 負傷 → ダウン → 拘束 → 救助 or 脱落（救助可能な猶予と再拘束ルールを別途確定）。
- 救助後は短時間の逃走猶予を与える。ただし無敵の連鎖でハンターを無力化しない。
- 「拘束」はロケットチェアの複製ではなく、廃墟の**封鎖装置**によるオリジナル表現を検討する。
- v0.5最小構成では、ダウン地点で短い確保動作後に拘束装置が作動する方式を試す。瞬間移動で捕獲させない。
- 自力救出の有無、拘束時間、2回目の確保の影響は難易度テスト後に決める。
- 立ち回りで助けられる余地を確保するため、ハンターの永久キャンプ対策はゲームルールとして検討する（例: 他地点の解読が進む代償）。

## 5. 各役割の行動と面白さ
| 役割 | 主行動 | 緊張・判断 |
|---|---|---|
| 解読役 | 修復対象を優先 | 近くで物音がした時に続行するか撤退するか |
| チェイス役 | 追跡を地形で振り切る | 板/窓/角のどこを使うか |
| 救助役 | 仲間の拘束解除、負傷仲間への支援 | 今助けるか、解読を進めるか |
| 潜伏役 | 視線を切る、索敵を避ける | 迂回して修復・救助へ戻るタイミング |

**固定ロールの強制はしない**。全員に基本行動を持たせ、状況で役割が変わる。

## 6. 味方BOTの設計 — 最重要
各BOTは以下の状態/役割を持つ:
- MOVE_TO_OBJECTIVE / REPAIR / EVADE / RESCUE / SUPPORT / OPEN_GATE / ESCAPE / INCAPACITATED
- 一定間隔で各仕事の優先度を再評価。目の前の状況で毎フレーム目的が切り替わる振動を防ぐ（ヒステリシス）。
- 複数BOTが無駄に同じ修復対象へ殺到しないように、**タスク予約**・担当の再割り当てを行う。
- 救助へ向かうBOTは原則1人。救助が危険すぎる場合は無理に突っ込まない。
- 追跡されたBOTは解読を中断し、逃走行動へ切り替える。逃走開始時は味方の解読機から離れる選択ができる。
- 目標位置は共有できても、ハンターの正確な座標は共有視界・通報・直近目撃からしか分からない（全知BOT禁止）。
- BOTはあえて失敗する「接待AI」ではなく、情報と操作制約のある合理的な味方。
- プレイヤーが何もしなくてもBOTだけで完勝するバランスは避ける。BOTの戦術能力と解読効率をログで可視化。
- 少なくとも「解読中」「追跡中」「救助へ移動中」「拘束中」「脱出中」の状態をチームHUDで表示。
- プレイヤーの指示は最小から。初期案は「救助要請/危険」の2つの簡易ピンだけ。実際に役立つか検証して増減。

## 7. ハンターBOT — 4人の知覚と追跡
- 4人それぞれの最後の視認位置、視認時刻、聞いた音を保持する。
- 状態: 巡回 / 音調査 / 個別ターゲット追跡 / 最終目撃地点の捜索 / 拘束処理 / 重要地点防衛。
- 追跡対象は**見えている/聞こえた相手**と切り替えコストによって決める。全サバイバーの真の位置は使わない。
- 追跡中に別人が見えた場合、距離・捕獲見込み・重要拠点への危険で優先を再判定。毎秒ターゲットをころころ変えない。
- ハンターが1人を追う間は他の解読が進められる。逆に解読に人が集中すると追跡が始まる危険がある。
- 拘束場所に無限に張り付くと一方的になるので、周辺防衛のルールとプレイヤー側の対抗手段を設ける。
- 難易度は移動速度より **索敵の情報・判断・追跡継続の妥当性** で調整する。

## 8. マップ
- 既存1600×1050の1vs1マップは暫定素材扱い。人数が増えて狭すぎる／見通しが悪すぎるなら拡大・再配置する。
- 修復点7、出口2、最低2つのチェイス用ループ、開けた危険地帯、複数の侵入路と救助ルートを設ける。
- 強い隠れ場所は安全な永続待機地点にしない。隠れる先は目的につながる必要がある。
- 「近くの修復点にいつもBOTが溜まる」「出口前で引っかかる」「拘束装置が壁に埋まる」などを自動検証対象に。

## 9. モバイル操作/HUD
- 優先ボタン: **移動スティック / 調べる（長押し） / ダッシュ or 短時間回避 / しゃがむ**。
- 石ボタンは初期版から消す。救助は近接で**調べるボタンを文脈変化**させて処理し、ボタン増を防ぐ。
- 板や窓も可能な範囲で同じアクションボタン。対象優先順位は「救助 > 緊急回避 > 修復」等、意図しない自動切替を避けるUIで見えるようにする。
- 上部HUD: 4人の状態（負傷/拘束/行動/解読）、残り修復数、追跡警戒。大きな文字やミニマップで画面を塞がない。
- 指の置いた位置から始まるスティック（v0.4.1）を保持し、マルチタッチ/画面回転/端末のセーフエリアを検証。
- ゲーム内で起きた事象はタップ可能な短い通知で知らせるが、常時大量の文章を重ねない。

## 10. 段階導入 — v0.5の完成条件
**Stage A 構造プロトタイプ**: 4人（自分+3BOT）とハンターの生成、7修復点、2出口、BOTの分担、4人用カメラ/HUD。旧版と比較できる試験URL（本番未上書き）。

**Stage B チーム戦の成立**: ハンターが個別追跡する一方で、残りが修復を進める。ダウン/拘束/救助/脱落と勝敗集計。1試合最後まで進む。

**Stage C 遊びの成立**: 地形、チェイス、障害物、潜伏、救助判断、BOTの競合/衝突/無限ループ解消。石なしでも駆け引きが成立するか実プレイで判断。

**Stage D 操作・難易度**: スマホの持ち方ごとの入力検証、観戦・リスタート、難易度テレメトリと最終調整。合格後のみ公開版更新。

## 11. シナリオテスト（必須）
1. ハンターがBOTを追うと、他2人+プレイヤーが修復/救助を判断できる。
2. ハンターがプレイヤーを追うと、BOTは目標を進めつつ必要なら救助する。
3. ダウンした味方を救助するBOTは、無条件で突撃しない／誰も永遠に救助に行かない事態を避ける。
4. 全4人が同じ修復点へ集合して衝突しない。
5. 視線外・壁越しの4人の正確な位置をハンターが知ることはない。
6. ハンターが壁を挟んだ相手を無限追跡し続けない。
7. BOTが壁・拘束装置・出口で停止しない。
8. BOT3人だけで常に勝ち続ける、またはすぐ全滅するバランスになっていない。
9. プレイヤーが捕獲された/脱出したあと、試合のチーム結果が確定する。
10. 3脱出=勝ち / 2=引分 / 1以下=負け、ゲート未開放・全員脱落も処理。
11. iPhone縦/横、iPadで操作・HUD・同時入力・アクション優先が破綻しない。
12. 石がなくても「解読・チェイス・救助・潜伏」で十分な選択肢がある。

## 12. 反証と保留
- 大きなリスク: 味方BOTの自動進行が強すぎてプレイヤーが観客になる／弱すぎてストレスになる。
- 救助・拘束が複雑すぎるなら簡略化しても良いが、協力が消える簡略化はNG。
- 4vs1で潜伏だけだと試合が動かない。「修復を進めるほど索敵リスクが増す」構造を守る。
- 石は**役割がないなら削る**。キャラクター固有能力や陽動アイテムはコア成立後に再検討。
- 役割別キャラクター、プレイヤーによるハンター操作、本物のオンライン5人対戦は今は開発スコープ外。
- 原作に似せるより、短時間の4vs1ブラウザゲームで「何をやると勝ちにつながるかが分かる」ことを優先。

### 未決定（要ゲーム設計/試験）

**安全な進め方**: この設計の合意が出るまでは `main/index.html` を変更しない。実装する場合も専用ブランチ→テスト→比較→公開承認の順番。
